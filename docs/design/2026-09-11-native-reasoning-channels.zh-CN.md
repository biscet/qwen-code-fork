# 由原生服务统一管理 Qwen 推理通道

[English](2026-09-11-native-reasoning-channels.md) | [简体中文](2026-09-11-native-reasoning-channels.zh-CN.md)

状态：已实现，2026-09-11。原生 `qwen2` 与配套桥接服务已部署；网关检查及当前 Mac 的原生界面与历史检查通过。最终 DMG 已重新构建，界面版本标签 `2.1.15` 已验证。两次严格 prepared-CLI 冒烟检查均未通过语义断言，尽管引擎退出码为 0。尚未测试另一台 Mac。

## 问题与已确认的基线

Windows Qwen 路由曾在三个层级独立解释推理标记：llama.cpp、Mac 归一化桥接服务以及 HomeCode 的 OpenAI 转换器。它们的解释不一致，导致推理文本进入可见内容，或拒绝实际上已经完成的回答。

捕获的 llama.cpp `b10809-5266f24da` 流显示，原生 `auto` 提取会在推理句子内被引用的 `</think>` 处结束推理。可见通道随后包含该句的剩余部分和后续推理。原生解析器寻找第一个结束标记；推理预算采样器另有独立的结束匹配器。采样器的完成状态还会被最终内容中的字面量 `<think>` 再次激活。

修复之前，桥接服务请求 `reasoning_format: none`，解析文本标签，并要求根结束标记位于行首。原生服务在预算耗尽时可能在行中强制插入该标记；已有复现记录表明，桥接服务因此拒绝了有效回答。在 `reasoning_budget_message` 后追加换行修复了该场景，但没有建立统一协议。

对修复前 HomeCode 源码的回放还独立确认：正确的结构化响应如果以 `<think>literal</think>` 为最终内容，可能触发 `PROTOCOL_TAG_LEAK`，或者将这个字面量转成 thought 部分。转换之后，ACP、SDK 转录事件、Web Shell 和历史记录均保留独立的 thought 标志。

合成原生捕获与回放用例位于 `.qwen/e2e-tests/qwen-native-reasoning-2026-09-11/`，其中包括 `native-parser-replay-cases.json`。这些捕获是复现证据，并非保存下来的原始用户对话内容。

## 目标与范围

- 对选定的 Qwen 模板，由原生服务统一管理推理、最终内容及其阶段切换。
- 在桥接服务、Bifrost、HomeCode、工具、转录回放和下一次模型请求中保持结构化通道。
- 原样保留最终内容中的推理标签字面量，不重新解析它们。
- 保持模型、推理启用状态、推理强度、推理与输出预算、上下文大小、GPU 配置、MTP 配置和工具权限不变。
- 保留其他提供商的兼容行为以及支持多个推理块的模型行为，不做全局修改。

## 原生协议与状态归属

根据实际的原生 Qwen 模板配置选择单根协议，不依赖客户端部署别名。将该配置传递给解析和采样环节，不为所有基于标签的推理模型启用此协议。

由每个请求独立的原生状态统一管理切换：

```text
reasoning -> final content or tool output -> completed
```

最终内容不能重新激活推理。预算、延迟工具语法和响应导出器观察同一次切换。克隆、重置、推测接受及回滚必须与采样器一起保留或恢复该状态。未被接受的草稿 token 不得推进状态。

Qwen 线协议将位于行首、可带前导空格、制表符或回车、且不在围栏代码块内的根结束 token 保留为控制语法。这是行前缀规则，不需要向前查看完整独立行。行内引用的结束标签和围栏内的标签仍然属于推理数据。推理内部的开始标签不建立嵌套协议阶段。围栏开始行在至多三个前导空白字节后，包含至少三个连续反引号或波浪号；结束行使用相同字符，长度不短于开始行，后面只能有水平空白。围栏状态在换行时变化。传输分块边界绝不定义行或 token 边界。模板的直接工具标记也可以结束推理，其字节仍交给原生工具解析器处理。

这是明确保留的语法，而非声称解析器能够判断模型意图。仅把旧桥接匹配器移到原生代码，同时保留独立的采样器匹配器，不符合本设计。

预算耗尽会产生显式的原生强制切换事件。导出器遵循此事件，而不从生成字符串中猜测。采样器保留配置的强制 token 并直接记录边界；服务端和桥接服务都不通过插入换行来让文本匹配器达成一致。桥接服务不再通过修改 `reasoning_budget_message` 协调解析器。即使推理围栏尚未闭合，强制切换也有效。这不改变配置的预算，也不添加第二次模型请求。

原生流式及非流式序列化根据该状态输出 `reasoning_content`、`content` 和 `tool_calls`。`qwen` 配置保留包括空白在内的载荷 token 字节，移除结构性推理分隔符及生成的结束 token；后者始终不属于文本。计算偏移量时，提示预填充中的字面 token 字节仍予保留。进入最终内容后，推理标记字面量就是普通内容。完整工具调用可以在没有最终文本的情况下完成。如果响应在推理阶段结束，超时、取消、长度限制、上游失败或断连不得变成成功的最终回答。

## 桥接服务与 HomeCode 协议

配置的路由通过 `generationConfig.extra_body.reasoning_format: "qwen"` 显式选择原生 `qwen` 格式。请求构造和响应处理共同使用该设置。模型名称子串或者偶然出现的单个推理增量，都不足以选择此协议。只有在该端点的原生实现通过验收后，才能应用该设置。

桥接服务请求结构化格式，并处理字段名称兼容与终止状态。它不从 `content` 或结构化助手历史中解析标签。Bifrost 可以将 `reasoning_content` 暴露为 `reasoning`；此别名转换必须保持通道分离。

对此显式协议，HomeCode 将推理转换为 thought 部分，将内容转换为字面文本部分。它绕过标签式推理提取、推理标签泄漏启发式检查，以及仅因推理包含标签而触发的缓冲。原生增量确实是增量，所以两个文本通道也绕过累计快照猜测。工具身份和参数验证继续生效。其他路由仍保留现有兼容处理。如果独立的通用协议标签检查会拒绝合法字面内容，这些检查也必须尊重选定的结构化协议。最终内容中的字面 XML 不能触发客户端的二次工具调用恢复。

打包默认设置为受管的 `local-coder` 模型启用此格式。在 `.desktop-defaults-v4` 提前返回之前更新既有设置，但仅限该模型显式 `baseUrl` 为 `https://biscet-server.local:9454/v1` 或 `http://127.0.0.1:1235/v1` 的情况。同时支持旧版提供商数组和 `modelProviders.openai.models` 包装形式。未设置以及 `none`、`auto`、`deepseek` 格式迁移为 `qwen`，其他显式值保持不变。迁移仅修改该 JSONC 属性，保留注释和其他设置。它不创建新的迁移标记，不重写未变化的文件，也不恢复缺失的模型或设置文件。

受信任工作区初始化在符号链接检查之后，对既有的 `.qwen/settings.json` 应用同一迁移，且不依赖 MCP 安装记录。工作区的 `modelProviders` 会替换用户级提供商，因此只更新全局设置无法为工作区所拥有的路由启用该格式。迁移不授予 MCP 所有权，不恢复已删除的 MCP 条目，也不修改安装记录。不受信任的工作区仍不进入此初始化路径。

ACP 更新、SDK 块、渲染和持久化历史保留现有的类型分离。验收同时验证实时输出和回放；不引入渲染器文本清洗器。下一次请求从这些字段重建内容和推理，而不是扫描序列化后的混合字符串。

## 限制与决策

相同且未转义的字节或 token ID，无法同时表示保留的阶段分隔符和任意字面数据，并保证恢复意图。在推理中按字面使用保留边界，需要采用转义表示。仅改为基于 token 处理并不能消除歧义。

本设计保留模型训练时使用的协议，并定义其接受的线语法。它无法保证模型在有效切换到最终阶段后，绝不继续写类似推理的文字。如果要求覆盖所有未转义字面量及模型的语义意图，则需要不同的编码、模型协议或生成策略。这些改动不在本次修复范围内。

因此，部署说明必须描述已验证的通道和生命周期行为，而非语义上的确定性。增加超时、关闭推理、寻找最后一个标签，或者仅切换 `auto`，都不构成此次修复。

## 验证与验收

1. 使用捕获的 quoted-close 和 nested-literal 用例回放原生实现。补充自然根结束、行内标记、围栏标记、保留边界及不完整边界前缀，并覆盖任意分块和 UTF-8 拆分。
2. 验证预算计数、自然完成、句内与围栏内强制切换、最终字面量不会重新激活推理、延迟语法激活、采样器克隆与重置以及推测回滚。对比预算状态与导出的通道，而非只看最终显示文本。
3. 验证流式与非流式响应、仅有推理时的截断、取消、超时、上游错误与断连、有效的仅工具调用完成、拆分的工具参数、无效参数和工具结果后的继续生成。
4. 通过 HomeCode 回放结构化响应，最终内容包含字面开始与结束标签、独立标记及围栏 XML。验证内容不变，且推理在实时 ACP 事件、SDK 块、渲染器输入、持久化回放和发出的历史中保持独立。验证重复及前缀重叠的增量分块、主路由与精确路由和回退路由之间的隔离，并验证全局与受信任工作区设置中，两种允许端点和提供商形式下的安全合并桌面迁移，包括注释、自定义格式、缺失模型、重复运行及保留工作区 MCP 安装记录。
5. 为其他提供商配置运行针对性回归测试，包括明确支持多个推理块的配置。完成要求的构建、类型检查和受影响包检查。
6. 分别测试实际 Windows 原生构建、已安装的桥接服务、Bifrost 和打包的 HomeCode 运行时。源码测试不能代替已认证运行时或局域网证据。随结果记录原生构建指纹及生效设置。

验收要求：采样与序列化共享唯一可观察的阶段切换，最终字面内容端到端保留，有效工具继续经过现有验证路径执行，且未完成推理绝不被报告为成功的最终回答。

## 部署与回滚

在切换生产环境前，准备并验证原生二进制、桥接改动、路由设置和 HomeCode 产物。将旧二进制与设置作为配套回滚集合保留。等待受影响路由空闲后再重启。Windows llama.cpp 只能通过计划任务 `Codex-Windows-GPU-LLM` 管理；不得独立终止其子服务进程。

重启后先验证原生服务健康与指纹，再验证桥接健康，最后验证配置的 Bifrost/LAN 路由和 HomeCode。避免在过渡期间出现一个组件期待新协议、另一个仍提供旧协议的情况。如果验收失败，按同样的受管重启流程恢复配套的原生、桥接、客户端设置及产物。不得只回滚通道协议的一侧。

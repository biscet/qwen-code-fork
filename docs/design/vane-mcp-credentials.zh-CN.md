# 桌面研究 MCP 使用 Vane 凭据

[English](vane-mcp-credentials.md) | [简体中文](vane-mcp-credentials.zh-CN.md)

## 问题

Vane 将 API 密钥保存在用户私有的 HomeChat 存储中，而内置
`home-ai-research` MCP 服务器从 Harness 环境中解析
`${LOCAL_QWEN_API_KEY}`。因此，保存有效的 Vane 密钥后，研究 MCP
仍然无法连接。插件显示需要身份验证，项目悬浮信息也会如实显示五个服务器中
只有四个已连接。

## 设计

继续使用私有 HomeChat 存储作为显式 Vane 密钥的来源。在桌面模式中，只有
合并后生效的 `home-ai-research` 配置的端点恰好为
`https://biscet-server.local:9454/research/mcp`，且其原始授权标头为
`Bearer ${LOCAL_QWEN_API_KEY}` 时，才为其应用该密钥。保留作用域优先级，
并通过最终胜出的原始定义识别托管模板。

仅在合并后的设置视图中应用覆盖值。保留原始设置和序列化配置，不修改
`LOCAL_QWEN_API_KEY`、模型凭据、Codex 凭据或其他 MCP 定义。没有保存的
Vane 密钥时，保留现有的环境回退逻辑。自定义端点和显式配置的授权标头维持
各自的行为。重新打开桌面应用时读取同一私有密钥，无需迁移。

进程全局的 `PUT /homechat/connection` 路由持久化有效密钥后，通过 MCP
协调器通知代次仍然开放的受管理、受信任运行时。协调过程使用各运行时自身的
桥接和重载队列。休眠运行时保持休眠，并在启动时读取当前设置；未知、不受信任、
已移除或代次已关闭的运行时不得回退到主运行时。

授权标头的变化会改变 MCP 配置的审批哈希。在安排协调前，守护进程按顺序为
符合条件的运行时刷新精确匹配的已安装桌面默认定义。现有初始化器会更新守护
进程的审批缓存和持久化记录，只识别未经修改的安装器托管定义，并保留显式
拒绝决定。这也使守护进程中的 Codex 工具清单保持最新。在 ACP MCP
重载期间，先从磁盘读取更新后的审批，再重新计算准入结果。子进程仅刷新自身
缓存，不写入相互竞争的审批快照。复用现有审批检查，不削弱其约束。

## 状态与使用方

继续根据实际 MCP 发现结果报告状态。成功通过身份验证的连接已经会清除之前
的身份验证要求；插件状态和项目悬浮计数使用该结果。仅保存密钥不能宣称服务器
已连接。合并后的配置还为新的 Qwen 会话和 Codex 工具清单提供设置，后者会
在每次提示时刷新。

## 验证与验收

- 在修复前，使用已保存的合成 Vane 密钥以及不同或缺失的 Harness 密钥复现
  无法连接的配置。
- 验证保存和重新打开后，托管研究服务的标头使用已保存的密钥，同时设置文件
  保留模板，其他凭据不变。
- 验证自定义端点、自定义标头、非桌面运行方式及未保存凭据的情况维持现有行为。
- 验证仅在持久化成功后为符合条件的运行时安排协调。刷新审批哈希时，不得批准
  已拒绝或被修改的定义，并覆盖运行中的 ACP 进程。
- 验证运行时发现结果仍是身份验证状态和计数的依据；源码测试与原生应用、浏览器
  或远程服务验证证据分别记录。

此变更不重新构建、打包、重启或部署桌面应用：用户仅要求源码修改、针对性检查、
提交和推送。测试夹具或输出中不得使用真实凭据。没有尚未解决的设计问题。
